01 / PRODUCT REQUIREMENTS DOCUMENT

PRD: JB³ AutoSocialAi

Problem Statement

Creators and founders lose 6-10 hours weekly adapting one idea across multiple platforms. Inconsistent posting stalls growth, while copy-pasting triggers platform algorithmic penalties.

Proposed Solution

An AI-native system that ingests a single 4-line idea and outputs a fully scheduled, platform-native, human-approved week of content, featuring a compound learning loop.

Success Metrics (KPIs)

  • → Time-to-publish reduced by 90%
  • → 100% human approval rate before publish
  • → 0% silent publish failures
  • → 20% MoM engagement growth via compound loop

Core User Stories & Acceptance Criteria

STORY 1 Content Generation

As a creator, I want to input a topic, audience, goal, and CTA, so that the system generates a master post and 8 platform-specific adaptations.

Acceptance: System returns 9 unique hooks. No phrasing is reused across platforms. Output is structured via Zod schemas.
STORY 2 Human Approval Gate

As a user, I want to review and edit AI-generated content in a unified queue, so that I maintain brand voice control before publishing.

Acceptance: Status remains READY until explicit approval. Edits are versioned. No auto-publish occurs without APPROVED status.
STORY 3 Honest Publishing & Failure Handling

As a user, I want to know exactly when a post fails to publish, so that I can manually intervene and never assume content is live.

Acceptance: Failed API calls immediately transition status to FAILED. User receives alert. System never silently retries >3 times or marks as PUBLISHED without platform confirmation.
STORY 4 Compound Analytics Loop

As a creator, I want the system to analyze past performance and feed insights into the next idea generation, so that my content improves weekly.

Acceptance: Metrics are pulled every 6h. Unavailable metrics are marked N/A. Top performers are embedded and retrieved during the IDEA phase.
02 / ARCHITECTURAL LAYOUT

System Architecture

High-Level Component Diagram

Architectural Principles

  • ✓ Event-Driven: Asynchronous workflows via BullMQ. No blocking HTTP requests for AI generation.
  • ✓ Durable Execution: State machines persist across restarts. A server crash doesn't lose a scheduled post.
  • ✓ Strict Tenant Isolation: Row-Level Security (RLS) in Postgres + workspace_id scoping in all queries.
  • ✓ Adapter Pattern: Platform APIs are abstracted. Adding a new platform requires zero changes to the core workflow engine.

Security & Compliance

  • ✓ OAuth Vault: Platform tokens encrypted at rest (AES-256), scoped per workspace.
  • ✓ No Browser Automation: Strict adherence to official APIs to prevent account bans.
  • ✓ Audit Logging: Every publish attempt, token refresh, and user edit is immutably logged.
  • ✓ Rate Limiting: Token bucket algorithm per workspace × platform to respect API quotas.

DATABASE
PostgreSQL + Prisma

Primary relational store. Row-Level Security (RLS) for multi-tenancy. JSONB for flexible platform metadata. Neon for serverless scaling and branching.

QUEUES & CACHE
Redis + BullMQ

Durable job queues for AI pipelines and publishing. Rate limiting via token buckets. Session caching. BullMQ ensures retries and dead-letter handling.

AI / ML
Vercel AI SDK + LiteLLM

Provider-agnostic model routing. Tiered model strategy (Opus for reasoning, Sonnet for adaptation, Haiku for mechanical). pgvector/Qdrant for semantic retrieval.

INFRA & OBS
Vercel + Railway + OTel

Frontend on Vercel edge. Backend workers on Railway. OpenTelemetry for distributed tracing across AI calls, queues, and DB queries. Axiom for log aggregation.

The Core State Machine

Every piece of content flows through a strict, auditable state machine. Transitions are triggered by user actions, cron jobs, or webhook events.

DRAFT
READY
APPROVED
SCHEDULED
PUBLISHED
or
FAILED
Transition Rules
  • → DRAFT → READY: AI generation completes successfully and passes the Judge Model quality gate.
  • → READY → APPROVED: User explicitly clicks "Approve" in the UI. Edits reset to READY.
  • → APPROVED → SCHEDULED: Scheduler worker resolves optimal time based on workspace prefs + historical data.
  • → SCHEDULED → PUBLISHED: Cron triggers publish worker. Platform API returns 2xx with confirmed media ID.
  • → ANY → FAILED: API returns 4xx/5xx, token expired, or rate limit exceeded. Alert sent to user.
Automation Triggers
  • ⏱ Cron (Every 30s): Scans for SCHEDULED posts due for publishing. Enqueues to platform-specific worker queues.
  • ⏱ Cron (Every 6h): Pulls analytics metrics from connected platforms. Updates engagement rollups.
  • 🪝 Webhooks: Ingests real-time events (e.g., token revocation, platform rate limit warnings) to update account health.
  • Event Bus: Internal events (e.g., `post.published`) trigger downstream analytics indexing and embedding updates.

Core Data Entities (Prisma Schema Overview)

model Workspace {
  id String @id @default(cuid())
  name String
  brandVoice Json? // Tone, forbidden phrases, examples
  users User[]
  posts Post[]
}

model Post {
  id String @id @default(cuid())
  workspaceId String
  status PostStatus // DRAFT | READY | APPROVED | SCHEDULED | PUBLISHED | FAILED
  masterContent Json // Hook, Body, Value, CTA
  platforms PlatformPost[]
  scheduledAt DateTime?
  publishedAt DateTime?
}

model PlatformPost {
  id String @id @default(cuid())
  postId String
  platform Platform // INSTAGRAM | TIKTOK | LINKEDIN...
  adaptedContent Json // Platform-specific text, media refs
  caption Json
  externalId String? // ID returned by platform API upon publish
  metrics Json? // Views, likes, etc. Null if N/A
}
